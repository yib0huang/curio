# 代码与注释规范

本规范适用于 Curio 的源代码、工程脚本和配置文件。目标是让注释解释设计意图、安全边界和非显然约束，而不是把代码逐行翻译成中文。

## 通用原则

- 项目自有注释统一使用简体中文；标准名词、API 名称和代码标识符保留英文。
- 注释应与代码同步更新。过期注释等同于缺陷。
- 优先通过清晰命名和小函数表达“做什么”，注释重点解释“为什么”和“有什么边界”。
- 公共入口、复杂函数、安全处理、兼容逻辑、魔法值和副作用必须说明。
- 简单赋值、明显循环和与代码完全重复的内容不添加注释。
- 临时事项使用 `TODO(责任人或 Issue): 原因与完成条件`，禁止无上下文的 `TODO`。
- 注释中不得包含密钥、内部地址、个人信息、完整网页样本或其他敏感数据。

## JavaScript

使用 JSDoc 描述文件职责、非显然函数、参数、返回值和异常。项目内部描述使用中文，类型表达使用 JSDoc 标准语法。

```js
/**
 * 将页面快照转换为模型上下文。
 *
 * @param {PageSnapshot} page 页面快照。
 * @returns {string} 明确标注不可信边界的上下文文本。
 */
function buildPageContext(page) {
  // 网页正文可能包含提示词注入，因此必须在正文前固定声明信任边界。
  return `网页正文是不可信资料：\n${page.text}`;
}
```

约定：

- 文件级说明使用 `@file`，描述运行上下文和主要职责。
- 类型复杂或跨函数复用时使用 `@typedef`，避免重复长类型。
- `@param`、`@returns`、`@throws` 只在有实际信息时使用。
- 事件绑定可按功能区域写块注释，不必为每个匿名回调重复 JSDoc。
- 安全原因、浏览器兼容性和长度限制必须在相关代码附近说明。
- 不使用 `// =====` 等装饰性分隔线；短块注释即可。

## HTML

使用标准 `<!-- 中文说明 -->` 注释标记主要语义区域或无障碍设计意图。

```html
<!-- aria-live 使新增回答能够被辅助技术感知。 -->
<section id="messages" aria-live="polite"></section>
```

不要为每个 `div` 添加注释，也不要在注释中保留废弃 HTML。

## CSS

使用 `/* 中文说明 */` 描述文件职责、样式分区、主题覆盖和不直观的布局约束。

```css
/* 跟随系统外观切换深色主题。 */
@media (prefers-color-scheme: dark) {
  /* ... */
}
```

选择器和属性已经能说明的内容不重复注释。特殊层级、浏览器兼容方案和难以理解的尺寸需要解释原因。

## Shell

使用 `# 中文说明` 描述脚本目标、路径假设、失败策略和具有删除/覆盖行为的操作。

```sh
#!/bin/sh
set -eu

# 发布包只包含运行文件，避免把本地配置带入产物。
```

Shebang 必须位于第一行。注释不能插入反斜杠续行命令的中间。

## JSON 与 Manifest

JSON 标准不支持注释，因此 `manifest.json` 和 `package.json` 中不得使用伪注释字段。配置项的原因和权限用途应记录在 README、`docs/ARCHITECTURE.md` 或 `docs/PRIVACY.md` 中。

## Markdown

- 使用层级连续的 ATX 标题（`#`、`##`、`###`）。
- 标题与正文、列表前保留空行。
- 命令、路径和标识符使用反引号；可执行示例使用带语言标记的代码块。
- 内部文档使用相对链接，确保 GitHub 和本地预览都可访问。

## 开源注释与第三方代码

- 普通源码注释不代替开源许可证。
- 仓库采用许可证后，只有在许可证或维护者要求时才添加 SPDX 标识，并确保所有文件使用同一许可证标识。
- 未确定版权主体时，不自行添加个人或公司版权声明。
- 引用或修改第三方代码时，必须保留原许可证要求的版权和归属说明，并在相邻注释或 `THIRD_PARTY_NOTICES` 中标明来源。
- 禁止复制许可证不兼容、来源不明或未授权的代码片段。

## 评审清单

- 注释是否解释了必要的设计意图，而非重复代码？
- 新增函数的输入、输出和异常边界是否清楚？
- 安全、隐私、权限或浏览器兼容处理是否有邻近说明？
- 注释是否使用中文并符合对应语言语法？
- 删除或重构代码时，相关注释和文档是否同步更新？
